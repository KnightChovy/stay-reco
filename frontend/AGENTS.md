# StayReco Frontend — Project Context and Conventions

This document applies to the entire `frontend` directory and is intended for developers and coding agents. **Current state** describes the existing source; **conventions** apply to new or modified code and do not imply that all existing code follows them. Update this document when the architecture changes. Keep the `nextjs-agent-rules` block above intact. `CLAUDE.md` references this file.

## 1. Product and implementation status

- StayReco has interfaces for hotel booking, travel recommendations, an AI assistant, and operations management.
- The primary UI language is Vietnamese (`lang="vi"`), using Be Vietnam Pro via `next/font/google`.
- Most screens currently use sample data and local state. A button, success message, payment page, or AI page existing in the UI does not imply a backend integration.
- Authentication is currently mocked with Zustand and localStorage. An API client and React Query provider exist, but there are no business API calls in `src` yet.
- Roles are `customer`, `partner`, `staff`, `manager`, and `admin`. Actor route trees now exist for all five roles. The `partner` and `manager` portals are under active migration, with their routes wired to `src/features/partner` and `src/features/manager` respectively.
- Partner hotel onboarding is connected to the backend (`docs/api/partner.md`): `/partner/dashboard`, `/partner/hotel`, `/partner/rooms`, `/partner/staff`, and `/partner/verification`. The partner portal uses no mock data: routes whose API does not exist yet (bookings, revenue, availability, pricing, promotions, loyalty, AI brand) render `PartnerUnavailable` naming the phase in `docs/phases` that will deliver them.
- The staff shell and the booking detail screen are connected to the backend: `StaffHotelProvider` loads `GET /me/hotels` and `GET /hotels/:id` for the assigned hotel, and `/staff/bookings/[id]` loads `GET /bookings/:id` (staff need `BOOKING` or `REFUND`). The staff booking list, check-in/out, refunds, inbox and alerts screens still use sample data because their APIs are not published yet; `GET /hotels/:hotelId/bookings` is the missing endpoint that unblocks the list.
- `/account/profile` (`GET /auth/me`, `PATCH /me/profile`, `POST`/`DELETE /me/avatar`) and `/account/security` (`POST /auth/change-password`, `GET`/`DELETE /auth/sessions`, `POST /auth/logout-all`) are connected through `@/features/account/api/account-queries`; form fields the backend does not store (address, ID number) were removed. `/staff/dashboard` reads `GET /hotels/:id/stats/today`, `/action-items` and `/stats/occupancy-forecast`. `/staff/refunds` lists `GET /hotels/:id/bookings?paymentStatus=REFUND_PENDING` (and the refunded ones) and forwards a request with `POST /bookings/:id/forward-refund`; the partner decides. The hotel and room type pages edit the stay with `StaySearchBar showDestination={false}`, which replaces the URL query. The voucher QR (`GET /bookings/:id/voucher` `qrToken`) is drawn in the browser by `VoucherQr` (`qrcode`) on `/account/bookings/[id]` and `/booking/confirmation`; `/staff/check-in` and `/staff/check-out` read it with `QrScannerDialog` (camera or a photo, decoded by `jsqr`) and look the booking up by `qrToken`. The staff shell shows the shared `NotificationBell` (`allHref={null}`), sidebar counts from `GET /hotels/:id/action-items` (refunds, overdue check-outs, change requests) and sends the header search to `/staff/bookings?search=`. `/staff/rooms` is the housekeeping board (`GET /hotels/:id/rooms`, `POST /rooms/:id/clean`); `/staff/availability` is read-only: rooms on sale per night (`GET /hotels/:id/availability`), the nightly price from `GET /room-types/:id/listing` and `GET /hotels/:id/pricing-rules`. The header has an "Ưu đãi" item ("Sắp có") to `/promotions`, a coming-soon page until the phase 4 promotions API exists. `/accept-invitation?token=…` calls `POST /auth/invitations/accept` and signs the invited account in.
- Phase 5 staff marketing is connected (`docs/api/marketing.md`) through `@/services/marketing.service` and `@/features/staff/api/marketing-queries` (`marketingKeys`), with shared parts in `@/features/staff/marketing` (`MarketingHeader`, status/platform pills, `AiBudgetCard`, `MarketingErrorPanel`, `GenerateContentDialog`, `SchedulePanel`) and labels in `@/features/staff/lib/marketing-labels`: `/staff/marketing/content` (AI budget, the brand voice read only, ideas from `marketing-content/ideas`, the AI writer, the content list by status), `/staff/marketing/content/[id]` (edit a `DRAFT`/`REJECTED` piece and its picture, submit for approval, delete, the owner's rejection reason, schedule an `APPROVED` piece on a connected page or "Đăng ngay" with a null `scheduledAt`), `/staff/marketing/calendar` (schedules by day, polled while one waits, cancel, the failure reason, connected pages read only) and `/staff/marketing/analytics` (published posts, the latest reading against the previous one, refresh). Every marketing endpoint but the budget needs the `MARKETING` permission, which `/me/hotels` does not expose, so a `403 FORBIDDEN` is shown as a missing permission (`getMarketingErrorMessage`). No `GEMINI_API_KEY` on the server makes the writer answer `503 AI_UNAVAILABLE`, which the dialog says. Owner actions (approve/reject, connecting pages, learning the brand voice) are not connected; nor is TikTok.
- Phase 4 customer screens are connected (`docs/api/promotions.md`, `loyalty.md`, `customer-wallet.md`, `reviews.md`) through `@/services/rewards.service` and `@/features/account/api/rewards-queries` (`rewardsKeys`): `/account/rewards` (StayMiles balance, tier and history from `GET /me/loyalty` and `/me/loyalty/entries`, personal codes from `GET /me/vouchers`; there is no points catalogue or code redemption there, codes are typed at booking), `/account/wallet` (`GET /me/wallet`, `/me/wallet/transactions`; withdrawing is not built until phase 6 and the screen says so), `/account/preferences` (`GET`/`PUT /me/preferences`; this screen owns the keys `travelStyles`, `roomAmenities` (comma-separated ids), `favouriteCity` and `budgetPerNight`, which the phase 5 recommender reads; an empty value is sent as `null` to remove the key), and `/account/bookings/[id]/review` (criteria from `GET /rating-criteria`, one star picker each, the overall rating previewed but computed by the backend; edits a written review while `review-eligibility.closesAt` is ahead, read back from `GET /me/reviews` since there is no `GET /reviews/:id`). The booking detail shows "Viết đánh giá" / "Xem đánh giá của bạn" from `GET /bookings/:id/review-eligibility` for a `COMPLETED` stay. `/booking` lists the customer's usable vouchers for that hotel in `VoucherPicker` (`@/features/booking/components`; `useVoucherOptions` prices each code with its own discount quote), pre-selects the one that saves the most ("Tốt nhất") until the customer picks another, "Không dùng voucher" or a typed code ("+ Nhập mã khác"), and prices the stay with `POST /bookings/discount-quote` (the automatic campaign, the chosen code and `pointsToUse`) and sends its `expectedTotal`, `code` and `pointsToUse` to `POST /bookings`; never compute a discount in the FE. `/booking/payment` offers "Thanh toán bằng ví" (`POST /bookings/:id/pay-with-wallet`, whole booking only) when the wallet has a balance. The hotel page ends with `HotelReviews` (`@/features/reviews/components`: `GET /hotels/:id/rating-summary` and `/reviews`) and shows the average in the hero. `StarDisplay` / `StarInput` in the same folder draw and pick scores. The partner phase 4 screens (promotions, review moderation) are not connected.
- Partner hotel onboarding is connected to the backend (`docs/api/partner.md`): `/partner/dashboard`, `/partner/hotel` (including the cancellation policy), `/partner/rooms`, `/partner/availability`, `/partner/pricing`, `/partner/bookings` (with refund approve/reject), `/partner/staff`, and `/partner/verification`. The partner portal uses no mock data: routes whose API does not exist yet (revenue, promotions, loyalty, AI brand) render `PartnerUnavailable` ("Sắp ra mắt" with the benefits; its `phase` prop names the delivering phase in `docs/phases` for developers and is never shown) and are `comingSoon` items in the sidebar (a "Sắp có" badge, no link).

## 2. Stack and development commands

Versions declared in `package.json`: Next.js **16.3.4**, React **19.2.8**, TypeScript 5 with strict mode, Tailwind CSS 4, and ESLint 9. Use npm and `package-lock.json`.

Main libraries: Base UI and shadcn (`base-nova`), Lucide, Zustand 5, TanStack Query 5, Axios, date-fns, and Recharts. React Hook Form, Zod, i18next, and TanStack Table are dependencies, but do not assume they are integrated into existing flows.

```sh
npm ci                    # Install exactly what the lockfile specifies
npm run dev               # Development server
npm run lint              # ESLint
npx next typegen          # Generate route types when missing or after route changes
npx tsc --noEmit          # TypeScript check
npm run build             # Production build
npm run start             # Run after a successful build
```

- The repository has no `test` script or configured test runner. Do not claim tests were run when none exist.
- `PageProps` and `LayoutProps` are generated by Next.js. Do not edit `.next/types` or `next-env.d.ts`.
- When integrating a backend, set `NEXT_PUBLIC_API_URL` in `.env.local` using the supplied environment value. There is no `.env.example`; do not invent an API URL or endpoints. `NEXT_PUBLIC_*` variables are exposed to the browser and must not contain secrets.

## 4. Code organization and imports

- Keep pages and layouts focused on routing and composition. Domain implementations live in `src/features/<domain>`; extend the established domain location and do not duplicate it under `src/components`.
- Keep feature-specific logic with its feature. Move a hook to `src/hooks` only when it is genuinely shared. Put business API calls in `src/services`; types shared across modules may live in `src/types`.
- Use PascalCase for components and types, `use` prefixes for hooks, and camelCase for variables and functions. Follow neighboring file/export names; do not rename unrelated code for cosmetic consistency.
- Keep TypeScript strict. Define props, inputs, outputs, and state unions clearly. Avoid `any`, casts that hide errors, or disabling ESLint instead of fixing the cause.
- Use `cn` from `@/lib/utils` in new feature code; do not add another class-joining utility.
- Import primitives from `@/components/ui/...` in new code. The `@/ui/*` alias currently resolves to `./ui/*` before `./src/components/ui/*`; do not assume it has only one source. `@/common/*` maps to `src/common`, not `src/components/common`.

### Working with shared components

- Shared UI lives in `src/components/common`. Before changing a component, find its imports with `rg` and confirm its actual file.
- AdminShell, StaffShell, ManagerShell, and PartnerShell use the common sidebar/navbar. Public pages use common cards, search, breadcrumb, and pagination.
- `TableCommon` in `src/components/common/table` accepts `columns`, `data`, `getRowId`, `isLoading`, and `emptyMessage`. It is a custom table wrapper, not a TanStack Table adapter.

## 5. Next.js and React rules

Before changing framework APIs, read the relevant guide for the installed version in `node_modules/next/dist/docs/`. Starting points already checked:

- `01-app/01-getting-started/05-server-and-client-components.md`
- `01-app/03-api-reference/03-file-conventions/dynamic-routes.md`
- `01-app/03-api-reference/04-functions/use-search-params.md`

Apply these conventions:

- Prefer Server Components for new pages and layouts. Put `'use client'` at the boundary that needs state, events, client hooks, or browser APIs. A single interactive button should not force an entire layout to be a Client Component.
- Do not access `window`, `localStorage`, or `navigator` during server rendering. Client Components must also be safe during prerendering; access browser APIs in an appropriate effect or event handler.
- Dynamic `params` are a Promise: use `await params` in a Server Component, or React `use` for a Promise prop in a Client Component; use `useParams` where appropriate. Do not copy older synchronous access patterns.
- On prerendered pages using `useSearchParams`, wrap the component reading query parameters in `Suspense`. Login/Register provide examples; development mode succeeding does not justify removing the boundary.
- Use `next/link` for internal links and `next/navigation` for programmatic navigation. Do not use Pages Router APIs such as `next/router` or `getServerSideProps`.
- Use `next/image` with alt text and appropriate dimensions or `fill` and `sizes`. The current image configuration permits any HTTP/HTTPS host; check existing image URLs before changing that policy.
- Clean up timers and listeners in effects. Avoid redundant derived state and effects that trigger endless state updates.

## 6. State, API, and auth

### State ownership for new code

- Use React state for local interactions and Zustand when client state must be shared.
- Use TanStack Query through the existing provider for client-side backend data. Do not create a QueryClient on every render. The provider isolates server instances and reuses the browser cache.
- Include every parameter that changes data (such as id, filters, or page) in query keys. After a successful mutation, update or invalidate the relevant queries; expose pending/error states and prevent duplicate submissions.
- Use `apiService` for client-side HTTP. It currently sets a JSON header, a 10-second timeout, and `NEXT_PUBLIC_API_URL` as baseURL; it has no token interceptor, refresh-token handling, or standardized error handling.
- Define DTOs from the backend contract before integration. Do not assume a `{ data, message }` response shape, endpoints, pagination format, or auth mechanism.
- Show loading, empty, error, and success states clearly. Do not catch an API failure and return mock data as if it were real. While a feature is mocked, keep sample data separate from API logic and state that limitation at handoff.

### Current authentication

- The active source is `useAuthStore`, `AuthUser`, `UserRole`, `roleDashboardPaths`, and `getSafeNextPath` from `@/lib/auth-store`.
- The store persists user and mock-account records under `stayreco-mock-auth`. Demo passwords are stored in plain text for the prototype; do not reuse this mechanism for real authentication.
- Demo access for these portals is generated by role: `partner@gmail.com` / `partner123` and `manager@gmail.com` / `manager123`. Successful login falls back to `/partner/dashboard` or `/manager/dashboard` through `roleDashboardPaths` unless a safe `next` path is supplied.
- `AuthRouteGuard` waits for `hasHydrated`, sends unauthenticated users to `/login?next=...`, and sends users with the wrong role to `/403`. Each prefix requires its exact role; admin does not automatically gain access to `/account`.
- Preserve hydration handling to avoid flashing authenticated UI or redirecting too early. When handling `next`, use the existing helper and ensure the destination stays within the app.
- The client guard only controls UI. When connecting a backend, the API/server must authenticate and authorize requests; do not trust role or user ID from localStorage.

## 7. Consistent UI, forms, and experience

- Reuse primitives in `src/components/ui` and read their implementation props before use. They are based on Base UI; do not assume Radix APIs such as `asChild`. Many components use a `render` prop.
- Color, typography, radius, and shadow tokens are in `src/app/globals.css` using Tailwind 4 (`@theme inline`). Prefer `bg-background`, `bg-card`, `text-foreground`, `text-muted-foreground`, `border-border`, `text-primary`, and semantic status colors.
- Use existing classes such as `sr-marketplace-container`, `sr-workspace-content`, `sr-page-title`, and `sr-section-title` where appropriate. Do not add a separate palette or font for each page.
- In the partner portal every clickable element (links, buttons, tabs, selects, menu/select options, checkboxes, switches, file labels) gets `cursor: pointer` from one rule in `globals.css` (`body:has(.partner-role) :where(...)`, unlayered so it also overrides the item primitives' `cursor-default` and reaches portaled dialogs and popups); disabled controls keep `not-allowed`. Do not add `cursor-pointer` per element there, and never put it on something that does not react to a click. Clickable things must be a `button`, a link or carry the matching ARIA role to get the pointer.
- Partner and manager layouts scope their portal tokens with `.partner-role` and `.manager-role`; both shells apply `.sr-dense-ui` only to the inner workspace. Keep those classes scoped to the actor portals and do not apply dense styles to the customer-facing area.
- Design responsively from small screens. Wide tables should scroll appropriately without overflowing the whole page.
- Icon-only buttons need accessible names; inputs need labels; dialogs need titles. Keep focus visible and controls keyboard accessible. Do not rely on color alone to communicate status.
- New forms need validation, field-level errors, a submit state, and clear outcomes. React Hook Form and Zod are available dependencies, but there is no established project form wrapper yet.
- Store Vietnamese content as UTF-8. Format money and dates for the relevant locale; prefer `Intl.NumberFormat('vi-VN', ...)` and date-fns with the `vi` locale. Do not calculate prices from formatted strings.
- i18next is a dependency without an observed translation setup. Header language and currency selectors currently use local state; they are not a complete i18n or currency conversion system.

## 8. Completion workflow

1. Read `git status`, the relevant page/layout and component, and their consumers before editing. Preserve existing changes by others; do not reset, delete, or restore unrelated files.
2. Determine whether the feature is mocked or connected to an API, which role uses it, and which component source to reuse.
3. Make focused changes in the correct module. Do not add dependencies or abstractions that duplicate existing functionality.
4. For code changes, run lint and typecheck; generate route types if needed. Run a production build when changing routes, layouts, providers, server/client boundaries, configuration, or before handing off a feature. For documentation-only changes, checking the diff, paths, and factual accuracy is sufficient.
5. **Mandatory final ESLint check:** every time you finish writing code, the last action before handoff must be running ESLint (`npm run lint`, or `npx eslint <changed files>` for a focused check). Do not report the task as done until ESLint passes. If it fails, fix the issues; if some errors are pre-existing or out of scope, state them explicitly with evidence instead of claiming a pass.
6. Check affected UI and flows on desktop and mobile, including empty/error/loading states, validation, filtering/pagination, and primary actions. For auth, check signed-out, correct-role, wrong-role, reload, and logout cases. For booking, check its steps and canonical URLs.
7. Review the diff for unrelated edits. At handoff, state what changed, what was checked, what remains mocked, and any unverified limits. If lint/build fails, distinguish existing failures from new ones with evidence; never report a pass for a failed or unrun command.

When adding routes, changing a shell, consolidating common components, connecting a real API, or replacing mock auth, update the corresponding part of `AGENTS.md` along with the code change.
